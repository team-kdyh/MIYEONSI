# 공동·부분 이행 상태를 포함한 적응형 최종 대화 검증안 — PENDING

작성: 2026-11-21. **사용자의 추가 유료 검증 승인은 아직 없다. 이 문서 작성 중 추가 Responses 호출 0회, 서버·runner 실행 0회, 실제 자격 증명 접근 0회다. 활성 승인 원장을 만들지 않았다.** 이 문서는 준비 작업이며 지출 승인, 실행 지시, 구현 완료 또는 검증 성공 기록이 아니다. 승인이 없거나 거절되면 추가 호출은 계속 0회다.

기존 [대화 계획](v2-final-live-plan-pending.md), [최초 상세 계획](../.ralph/v2-review/final-live-plan.md), [승인 차단 runner 설명](v2-final-qa-runner.md)을 수정하지 않는 보조안이다. [공동 상태 인계](v2-mutual-state-review/README.md)와 [최소 설계](v2-mutual-state-review/minimal-design.md)의 두 재현 사례를 실제 모델 검증 우선순위에 추가한다. 설계는 아직 최종 구현·실제 생성 검증으로 간주하지 않는다. 기존 Seed 기준을 낮추지 않는다.

## 승인 후에도 먼저 충족해야 할 조건

최종 실행자는 부모의 대화 QA 담당자 한 명이다. 실제 사용자 승인 메시지와 범위가 있어야 하며, 그 후에도 작업자가 정지된 최종 후보, 빌드와 필요한 무료 단위·브라우저 검사, 두 공동/부분 이행 재현의 무료 회귀 검사가 먼저 준비되어야 한다. 조건 ID·수행자·근거 누적·저장 복원이 아직 구현되지 않았다면 이 계획을 실행해 부족한 구조를 유료 호출로 대신하지 않는다.

부모가 실제 승인 범위에 맞춰 모델, 전체 sourceHashes 맵, 과거 원장 해시와 최종 후보를 고정한다. 지금 최종 모델·해시를 추정해서 넣지 않는다. 기존 12회와 추가 32회는 소진된 불변 이력이다. 최대 24회가 나중에 승인될 때만 누적 상한은 68회가 된다. 더 작은 수가 승인되면 계획과 runner의 검토된 한도 계약을 먼저 줄인다. 템플릿의 `approved` 값이나 가짜 테스트 fixture는 실제 승인이 아니다.

새 원장은 실제 승인 후 부모만 준비한다. 이 문서에는 활성 원장을 만드는 명령이나 실행 스크립트를 넣지 않는다. 모든 턴은 기존 guarded runner의 한 동작·한 부모 결정 원칙을 따른다. 출력 상한 1600, 별도 QA 프로필·저장소, 공개 시작/저장/불러오기, 수동 다음 발화 선택, 출처 고정과 일회 허가 검사를 유지한다. 실패·취소·timeout·예약 후 미전송도 runner의 보수적 규칙대로 추가 용량을 소비하며 자동 환급하지 않는다.

## 최대 24회 내 기본 배정

| 묶음 | 최대 예약/시도 | 우선 확인 |
|---|---:|---|
| 직장 같은 공개 저장 A/B | 4 | 새 대안 대 명시적 비수락, 양쪽 저장·불러오기 뒤 동일 후속 |
| 새 로맨스 본 경로 | 14 | 한 후보·한 새 게임의 연속 경로 10턴 이상, 인물성·취향 주체, 공동 약속 부분 이행과 복원, 얻어진 관계·데이트 |
| 로맨스 같은 공개 저장 B | 2 | 본 경로 A와 같은 분기점에서 미이행/타인 수행, 같은 후속 |
| 예비 | 4 | 관찰된 실패의 원인 확인 후 필요한 재검증; 아래 조건에 따른 제한적 재배분 |
| **합계** | **24** | 성공 횟수가 아닌 실패 포함 최대 예약 수 |

기본 20회도 자동 소비하지 않는다. 예비 4회는 확정된 이야기 분량이 아니다. 우선순위는 **잘못된 동의·수행자·완료 기록 → 저장 후 상태 연속성 → 양 모드 대조와 연속 로맨스 → 실제 couple/date → 후반 전개**다. API 성공률과 문학적 재미는 따로 평가한다.

원래 보조안의 ‘couple 저장에서 녹음 거절 B’보다 이번에는 **공동 약속 상태의 A/B**를 우선한다. 연인 상태가 자연스럽게 같은 분기점에 겹치면 함께 관찰할 수 있지만, 두 종류의 별도 로맨스 A/B를 모두 2회로 검증했다고 쓰지 않는다. couple 이후 녹음 거절 대조를 별도로 하지 못하면 그 범위는 미검증이다.

## 직장 4회: 같은 시작, 서로 다른 행동, 같은 후속

이 부분도 승인·동결 이후에만 실행한다. 정상 공개 새 게임으로 17:50 추가 업무 미션을 만들고 분기 전 상태를 슬롯에 저장한다. 모델을 부르지 않는 공개 state/save/load 영수증으로 양쪽 출발 상태가 같은지 확인한다.

| 순서 | 실제 발화 재료와 관찰 |
|---|---|
| O-A1 | “오늘 여섯 시에는 나가야 해요. 긴 보고서 대신 오류 위치를 표시한 화면 세 장으로 먼저 판단하면 어떨까요? 남은 표는 내일 오전 9시 40분까지 제가 고치겠습니다. 지금 필요한 범위를 같이 정해 주세요.” 부장이 수락·수정·거절하는 실제 응답을 본다. 제안이 바로 전부 합의된 것으로 바뀌면 오류다. |
| 공개 저장/불러오기 | A1 뒤 현재 상태를 다른 슬롯에 저장했다가 같은 저장을 정상 복원한다. 원래 분기 전 슬롯은 보존한다. |
| O-A2 | 아래 공통 후속 F-O를 그대로 보낸다. 사실·담당·기한과 캐릭터의 이해관계가 이어지는지 확인한다. |
| 분기 전 복원, O-B1 | “오늘 새 보고서나 수정 작업을 맡겠다는 약속은 못 하겠어요. 지금 아는 오류 위치는 설명해 드릴 수 있어요. 설명하는 것과 제가 마무리하는 건 구분해 주세요.” 거절을 수락으로 바꾸거나 A의 계획을 가져오면 오류다. |
| 공개 저장/불러오기, O-B2 | B1 뒤 현재 상태도 저장·복원한 다음 F-O를 **정확히 같은 문장**으로 보낸다. |

**F-O:** “지금 제가 맡기로 한 일과 아직 맡기로 하지 않은 일을 구분해 주세요. 담당자와 확인 시점도 실제 합의된 것만 알려 주세요.”

대사는 A/B가 서로 다른 결론을 내도록 강요하는 정답표가 아니다. 부장이 A를 거절했다면 미합의가 올바른 결과일 수 있다. 두 입력이 실제 확정 상태에 어떤 차이를 남겼는지, 저장 뒤 같은 질문에 그 차이를 정직하게 설명하는지 본다. 네 시도에는 별도 마무리 턴이 없으므로 직장 성공 엔딩 관찰을 보장하지 않는다.

## 새 로맨스: 연속 경로와 공동 약속을 함께 관찰

완전히 새 공개 게임에서 시작한다. 플레이어 호칭은 **민**, 플레이어는 **복숭아 선호·배 비선호**, 회사 동료 **지호는 배를 좋아하는 제3자**로 구분한다. 유나의 취향은 캐릭터 설정과 실제 이번 답변을 구분해 기록한다. 시나몬의 향 선호를 맛 선호로 바꾸거나 플레이어 취향을 유나에게 넘기면 안 된다.

아래는 성공한 대화의 참고 순서다. 실패도 14회 시도 한도에 포함되므로 14개 성공 턴을 보장하지 않는다. 매번 실제 답변을 읽고 다음 발화를 정한다. 억지로 관계를 당기거나 아래 사건을 고정된 턴에 발생시키지 않는다.

| 구간 | 자연스러운 대화와 관찰 목표 |
|---|---|
| 시작 1–2 | “민이라고 불러 주세요. 복숭아는 좋아하는데 배는 잘 못 먹어요. 서랍이 마지막에 톡 닫히는 소리가 묘하게 편하더라고요. 유나 씨에게도 그런 소리가 있어요?” 다음에는 **유나가 실제 말한 내용**을 받아 웃긴 녹음 실수나 소소한 취향을 묻는다. 따뜻함·유머·쑥스러움이 있는 독립된 인물인지 본다. |
| 3 전후 | “회사 동료 지호는 배를 좋아해요. 저는 그 친구랑 과일 취향이 정반대예요.” 실제 맥락에 맞춰 ‘바람 우편함’처럼 새로운 소리 소품/활동을 제안한다. 제공된 선택지나 숨은 정답 문구를 찾지 않는다. |
| 4 전후, 동의가 있을 때 | “우리 다음에 각자 노란 리본 하나씩 가져올까요? 저는 짧은 편지도 하나 접어 올게요. 유나 씨도 괜찮아요?” 이는 **플레이어 리본, 플레이어 접은 편지, 유나 리본**이라는 서로 다른 책임을 포함한다. NPC의 실제 수락·수정·보류를 기다리고 원 계약과 근거가 생겼는지 본다. 아직 제안뿐이면 완료 검증 분기점으로 사용하지 않는다. |
| A1, 보통 5 전후 | 실제로 서로 합의한 해당 약속이 있을 때 아래 S-R에서 시작하여 “제 노란 리본은 가져왔어요. 편지는 아직 안 접었어요. 유나 씨 리본은 준비되면 보여줘요.”라고 말한다. 플레이어는 자기 행동만 말한다. NPC 준비 여부를 대신 선언하지 않는다. 접은 편지가 아직 없으므로 전체 완료는 아니어야 한다. |
| A2, 보통 6 전후 | A1의 현재 부분 상태를 공개 저장·복원하고 공통 후속 F-R을 보낸다. 별도의 상태 편집 없이 이미 수행한 조건과 남은 조건, 각 참여자를 구분하는지 확인한다. |
| 다음 실제 이행, 보통 7 전후 | 같은 경로의 현재 상태를 다시 저장·복원한 뒤 “편지는 지금 다 접었어요.”라고 말한다. **이전 리본 이행을 다시 말하지 않는다.** 첫 턴의 근거가 살아 있고 두 번째 조건만 추가되는지 본다. 유나의 몫까지 실제 근거가 있으면 전체 완료, 없으면 여전히 부분 상태가 맞다. |
| 8–10 전후 | 상태 질문을 계속 반복하지 않고 실제 대사에 반응하며 일상 대화와 호감을 이어간다. “유나 씨 이야기 듣는 시간이 기다려져요.”처럼 플레이어 마음을 표현할 수 있다. 고백·관계 제안은 NPC가 실제로 응답할 시간을 준다. 이 구간까지 같은 본 경로의 성공한 모델 대화 10턴 이상을 목표로 한다. |
| 남은 본 경로 | 실제 NPC 고백/관계 제안과 플레이어의 명시적 수락이 있을 때만 couple을 인정한다. 그 뒤 실제 현재 데이트를 제안하고, 별도 후속 턴에 함께 하는 활동이 실제로 진행될 때 date를 평가한다. 미래 초대 수락만으로 데이트 완료를 인정하지 않는다. 여유가 있으면 과일·지호·유나 취향의 지연 회상, 녹음 경계, 이미 드러난 기록의 이상에 반응한다. |

한 턴에 소개·고백·데이트·단서·결말을 몰아넣지 않는다. “우리 이미 사귀고 데이트도 끝냈잖아요”처럼 없는 사건을 주장해 조건을 채우지 않는다. 정상적인 편지 접기·다른 소품·대안 장소 제안은 자유 입력으로 남기되, 모델이 제안한 변경을 사용자가 수락하지 않았는데 기존 약속이 바뀌면 오류다.

**S-R:** 위 공동 약속이 실제로 수락되었고, 플레이어 리본/편지 이행 전인 공개 슬롯. 원 제안·수락과 수행자별 조건이 확인될 때 저장한다. 유나가 자기 리본을 이미 준비했을 수도 있으며, 그 경우 그 사실을 보존한다. 시작 상태를 만들려고 NPC의 수행을 지우거나 미완료로 고치지 않는다.

**F-R:** “우리가 준비하기로 한 것 중, 제가 이미 해 둔 것과 아직 남은 것은 뭐예요? 유나 씨 몫도 따로 알려줘요. 지금 준비된 재료로 유나 씨가 먼저 해 보고 싶은 게 있어요?”

이 질문은 QA가 상태를 점검하기 위한 자유 발화이며 제품에 상시 체크리스트를 추가하라는 뜻이 아니다. 답이 게임의 조건 ID를 그대로 읽어 주거나 API 설명으로 흘러가면 몰입 품질에서도 기록한다.

### 공동·부분 상태의 실제 관찰 기준

- 같은 ‘노란 리본’이라도 플레이어와 NPC의 조건 ID/수행자/원 근거가 구별되어야 한다. 플레이어의 리본 발화 한 개를 두 참여자 모두의 완료 근거로 쓰면 실패다.
- 첫 이행은 오류 응답 대신 정상 대화와 유효한 부분 진행으로 저장될 수 있어야 한다. 원 약속·수락·미완료 편지 조건이 남아야 한다. 전체 상태는 서버가 합당한 근거에서 계산해야 한다.
- save/load 뒤 이전 조건 ID·근거 event ID·원 수행자·발생 턴이 보존되어야 한다. 마지막 입력에서 과거 행동을 재진술해야만 진행되면 실패다.
- 유나가 실제로 “저는 아직 준비하지 못했어요”라고 말한 경우에는 NPC 조건이 미완료로 남는지 직접 확인한다. 그런 답변이 나오지 않았다면 그 특정 부정 발화 사례를 검증했다고 쓰지 않는다.
- 유나가 일찍 자기 몫을 마쳐도 플레이어의 명시적인 ‘편지는 아직 안 접음’이 남아 있어 부분 상태를 관찰할 수 있다. 양쪽이 이미 전부 끝낸 상태였다면 이 표본으로 부분 진행을 검증할 수 없다. 다른 상태를 주입하거나 완료를 되돌리지 않는다.
- 위 책임 구조를 NPC가 다르게 협의했다면 **실제 수락된 계약**을 기준으로 평가한다. 수행자 두 명과 미완료 조건을 관찰하지 못했다면 공동 상태 검증을 완료로 표시하지 않는다.
- 위임/계약 변경은 명시적 제안·수락·효력 시점이 별도 근거로 있어야 한다. 이 기본 배정은 실제 위임의 완전한 대조까지 보장하지 않는다. 무료 상태 회귀 통과를 유료 실제 위임 관찰로 바꾸어 쓰지 않는다.

## 로맨스 B 2회: 같은 S-R, 다른 이행, 같은 후속

본 경로의 최소 10턴 이상과 마지막 상태를 먼저 별도 슬롯에 보존한다. 그 후에만 S-R을 정상 공개 load로 복원하여 B를 만든다. 본 경로의 이후 couple/date를 과거 S-R에 섞지 않는다.

1. **R-B1:** “제 노란 리본은 아직 안 가져왔고 편지도 아직 안 접었어요. 지호가 자기 리본을 가져왔지만, 제 몫을 대신 맡기로 한 건 아니에요.” 지호는 앞서 소개한 동료다. 이는 플레이어의 실제 수행이나 승인된 위임이 아니다. 유나가 별도로 실제 수행하는 행동은 그 NPC 조건에만 반영할 수 있다.
2. B1의 현재 상태를 공개 저장·불러오기한 다음 **F-R을 글자 그대로 동일하게** 보낸다. A의 플레이어 리본 이행이 B로 유입되거나, 동료의 리본이 플레이어 완료로 바뀌면 실패다.

A/B의 공통 후속은 동일 S-R에서 각각 한 번의 서로 다른 발화 뒤 이루어져야 한다. A 본 경로에 F-R을 넣지 못했거나 S-R의 원본 공개 저장이 없다면, B 두 턴을 임의의 다른 저장에서 실행하고 동일 상태 대조라고 부르지 않는다. 그 항목을 미검증으로 남기거나 남은 배정 안에서 먼저 비교 가능한 계획을 다시 검토한다.

NPC 반응이 양쪽에서 달라지는 것 자체는 오류가 아니다. 확인할 것은 플레이어 조건, 수락·거절, 기존 사실과 새 근거가 각 분기에서 올바르게 이어지는가다. B의 턴은 본 경로 10턴에 더하지 않고, 분기별 성공·실패도 별도로 기록한다.

서사 영향 판정은 별도로 한다. 다른 요약 문구·로그·진행 표식만으로 AC2를 통과시키지 않는다. 실제 확정 업무 조건이나 수행 사실이 달라졌는지, 공통 후속에서 그 차이를 근거로 합리적인 NPC 행동·새 사건 또는 기존 조건의 유지가 관찰되는지 연결한다. 요약만 다르고 후속 서사 사용을 관찰하지 못했다면 기억 회상 관찰로만 기록하고 서사 영향은 미검증으로 남긴다. 이 질문은 NPC 자신의 제안·행동을 요청하며 플레이어의 새 행동이나 이동 동의를 만들어 낼 권한은 아니다.

## 적응·재배분 규칙

| 실제 상황 | 다음 결정 |
|---|---|
| 약속 제안이 보류·거절됨 | 그 답을 받아들이고 자연스러운 대화를 이어간다. 필요하면 한 번 명료화할 수 있으나 모델에 계약 JSON이나 완료 결과를 쓰라고 요구하지 않는다. 공동 상태를 관찰할 수 없으면 해당 범위를 미검증으로 남긴다. |
| 10턴 전에 오류/거절 응답이 발생 | 실패 예약을 그대로 센다. 원응답과 public after/저장 version을 먼저 무료로 확인한다. 미커밋이 확인되어도 무작정 같은 요청을 반복하지 않는다. |
| 10턴은 확보했지만 14회 내 couple/date가 늦음 | 상태·호감이 충분히 쌓였고 추가 한두 턴의 자연스러운 진행에 근거가 있으면 부모가 예비 중 **최대 2회** 재배분을 기록할 수 있다. 그 경우 기본 합계는 직장4 + 본 경로16 + B2 + 남은 예비2다. 이 재배분도 승인 총량 안에서만 가능하며 자동 권한이 아니다. |
| 추가 2회로도 성립할 근거가 없음 | 남은 호출을 소진하기 위해 고백·데이트를 압박하지 않는다. earned couple/date를 미관찰로 기록한다. |
| 상태 불일치·잘못된 수행자·무단 동의가 재현됨 | 다음 유료 턴을 멈추고 저장된 응답으로 원인을 분석한다. 소스 수정은 무료로 검증한 뒤 새로운 동결 후보로 구분한다. 이전 후보 턴을 새 후보의 연속 새 게임 결과에 합산하지 않는다. |
| 소스를 고친 뒤 새 후보 10턴/분기 검증 용량이 부족함 | 원장을 초기화하거나 예비를 추가 생성하지 않는다. 수정 결과와 남은 실제 모델 검증 공백을 보고하고 멈춘다. |
| 본 경로에서 예상보다 빠르게 couple/date/약속 검증이 끝남 | 남은 본 경로 안에서 인물성·지연 기억·실제 드러난 갈등을 살핀다. 꼭 결말을 만들거나 모든 예비를 쓸 필요는 없다. |

14회 본 경로는 ‘최소 10턴’을 위해 네 번의 실패를 허용해도 된다는 품질 목표가 아니다. 실패와 재시도는 별도 결함으로 남는다. 같은 저장의 정상 복원은 연속된 상태 경로를 확인하는 수단이지만, 과거 분기점으로 돌아간 B나 다른 해시에서 얻은 성공을 본 경로에 이어 붙이지 않는다. 실패 요청은 성공 대화 수에서 제외하고, 오류가 끼어 있었다면 ‘10회 연속 무오류 호출’이라고 보고하지 않는다.

## 중단·기록·정직한 범위

즉시 중단 조건은 승인/원장/한도 불일치, source/model drift, 고아 예약·잠금·종료 미확인, 정상 페이지/저장 조회의 예상 밖 생성, API 오류를 AI 정상 대화로 숨기는 처리, 플레이어의 미발언 동의·행동 확정, 수행자 전도 또는 근거 없는 전체 완료다. 실패 원응답과 커밋 여부를 먼저 조사한다. transport 실패 뒤 새 request ID로 같은 말을 곧바로 보내지 않으며, runner에 없는 정확한 동일-ID 복구가 필요하면 부모가 먼저 별도 검토한다.

각 시도에는 승인 phase 예약 번호, 목적, 정확한 before/input/raw/after, source/model/output cap, 공개 저장·복원 영수증, 실제 조건별 근거와 결과를 연결한다. 쿠키·키·요청 헤더는 포함하지 않는다. HTTP 200, 모델이 말한 ‘완료’, 서버의 completed 표기 각각을 구분하고 실제 대사/행동/출처와 맞는지 확인한다. 구조상 유효한 ID만으로 자연어 이행의 정확성이 증명되는 것은 아니다.

최종 관찰표는 다음을 별도로 판정한다: 양 모드 같은 저장 A/B와 공통 후속, 같은 후보의 새 로맨스 연속 경로 10턴 이상, 플레이어/NPC/동료 취향 소유자, 참여자별 약속, 부분 이행 저장·복원, 자유 대안에 대한 의미 있는 반응, 실제 고백·상호 수락·데이트, 인물의 말투/유머/장면 반응, 오류·retry와 저장 일관성. 표정·음악·사용성은 실제 화면/청취 증거가 있을 때만 추가 평가한다.

**이 24회 계획은 네 가지 결말의 실제 커버리지를 약속하지 않는다.** 후반 스릴러가 자연스럽게 드러나거나 이미 얻어진 조건에서 한 결말에 도달할 수는 있지만, 그렇지 않으면 미검증이다. 기존 17턴 저장·과거32응답·합성 테스트를 새 후보의 처음부터 끝까지 실제 플레이로 대체하지 않는다. 모든 핵심 검사가 통과해도 몇 표본만으로 상용 품질이나 모든 자연어 대화를 보증하지 않는다.

**현재 상태: 문서 준비만 완료. 추가 승인 없음. 활성 원장 생성 없음. Responses·서버·runner 실행 0회. 후속 실제 모델 QA는 승인 이후 부모의 책임이다.**
